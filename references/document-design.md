# SharedBrief content-led design default

SharedBrief's default for new proposals, sales memos, pitches, one-pagers and business briefs is polished, content-led design. Create a bespoke responsive static HTML/CSS document (format html, mode static) without asking the user to request styling. An explicit user format, brand or visual reference overrides these defaults. Ordinary text documents and explicit plain-text requests can use structured blocks. For a narrow edit, preserve the existing design, content, stable URL and access/publication settings.

DESIGN THE STORY: Decide what the reader needs to understand and do, then choose a visual composition that explains this particular subject. A sales proposal needs a clear offer, buyer benefit, credible support and next step. A product pitch may need a visual mechanism or comparison; a report may need evidence and changes over time. Do not force every genre into the same executive memo. Choose one coherent art direction from the subject's brand and audience: intentional typography, restrained color, generous whitespace and strong contrast. Light editorial pages and dark product presentations are both valid when they fit. Use system fonts with distinct display/body proportions; no external font imports.

COMPOSE, DO NOT JUST FORMAT: Lead with a dominant benefit headline (typically 40–64px desktop, 30–40px mobile), a concise explanation and a decisive visual idea. Establish a focal point rather than distributing attention evenly across small boxes. For a product proposal, let the product demonstration share the opening composition with the offer, instead of burying it below several paragraphs. Use an asymmetric layout or contrasting full-width moment when the content earns it, with generous quiet space around the focal visual. A literal memo or short text-only request need not add a diagram.

PRODUCT AS EVIDENCE: When proposing a product, show its distinctive mechanism through one substantial HTML/CSS visual: an illustrative approval screen beside a purchase receipt, a product anatomy with precise annotations, a meaningful before/after, or an equivalent artifact that makes the benefit concrete. Choose from the researched subject, never force a payment metaphor onto unrelated products. A row of labeled text boxes with arrows is not by itself a product demonstration. Show the important relationship, decision or changed state spatially, then remove copy that merely repeats the visual. Use authentic terminology and explain who controls what. Any reconstructed interface must be labeled illustrative, not a real screenshot, exact shipped interface or completed transaction; use clearly marked example values only when necessary. Present a static state or a complete static sequence with readable annotations, not controls that look clickable. Do not fabricate brand assets, customer logos, card credentials, testimonials or claims of product functionality.

Give different information different treatments: proof can be one well-supported fact with its caveat, rather than a mandatory metric strip; products can have distinct concise modules; a comparison can show the relevant alternatives together; customer evidence can be a tidy list; commercials can be one clear offer. Choose only structures justified by the content. Vary section rhythm and hierarchy within one coherent page. Do not repeat equal cards, tables, numbered sections and phase panels as a universal recipe. Avoid decorative UI that contributes no understanding, and do not invent fake toggles, replay buttons, inputs or controls for a static page. Preserve the explanatory value of an interactive reference using a complete static composition.

CRAFT: Center the page at a width suitable for its composition (usually 850–1100px), with generous desktop margins and 20–28px mobile padding. Use readable body text around 14–17px, comfortable line height, short paragraphs, clear section headings, deliberate alignment and consistent spacing. For a one-page request prioritize roughly 250–400 words and a focused visual story; omit secondary detail before shrinking text. A one-page web brief is one coherent document, not a fixed-height canvas. Avoid a long mini-website or a compressed brochure. Keep only the buyer problem, the product mechanism, the strongest support and a clear offer/next step when those are relevant; there is no mandatory section list. Remove secondary product catalogs and repeated benefit lists before reducing whitespace. Use a small deliberate type scale, short heading lines, consistent alignment and a restrained accent repeated with purpose. Avoid excessive uppercase micro-labels and tiny footnotes as a substitute for hierarchy. No forced section count, preparation metadata or clerical To/From fields unless useful.

Do not default to terminal windows, shell commands, monospace body copy or developer panels merely because the subject is technical. Actual code or a transaction trace belongs only when necessary to explain the product; it must not replace the main visual story. Do not rely on decorative gradients, emoji, generic icons or placeholder badges for visual quality.

TRUTH AND USABILITY: Use available source material and the user's facts. Do not invent proof, metrics, prices, implementation dates, commitments, testimonials, brand assets or contact addresses. Label proposed rollout steps and assumptions clearly; distinguish current results from targets and keep material limitations visible. Use semantic markup, accessible contrast and descriptive links. Stack or recompose columns and diagrams on narrow screens; constrain long text and tables to avoid horizontal overflow. Set box-sizing:border-box. Do not fix page height, clip content or add internal scrolling. All content must be visible without a click or scroll-triggered reveal.

DESIGN REVIEW: Before the first save, critique the full composition once: can the reader grasp the offer and mechanism at a glance; is there one unmistakable focal visual; does each section add information; are claims supported; and will the narrow-screen composition remain legible? Revise generic diagrams, uniform cards, dense copy and weak hierarchy before saving. If the host has a rendering/browser tool, inspect the actual desktop and mobile rendering and correct concrete defects in one bounded pass. If it has no such tool, review the source/layout and do not claim visual verification. After saving, show the actual draft with the preview tool when available; a preview call alone does not prove visual inspection. Never publish a draft to make inspection possible.

CAPABILITIES: Use a self-contained style block and HTML/CSS. SharedBrief supplies viewport/security metadata. No scripts, event handlers, images, SVG, external dependencies, forms, iframes, trackers or meta elements. Do not promise unsupported interaction. Create new briefs privately and show the draft using the preview tool when available. Preserve existing publication state during edits. Publish only on the user's authorization.
